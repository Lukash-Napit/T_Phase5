# A5 Reflection

## A pagination/filtering design decision I'm proud of

I made the pagination-parameter validation reject malformed input with a `400` rather than silently falling back to a default — `?page=-1` or `?limit=abc` both produce a structured error naming exactly which parameter was invalid and why, instead of quietly treating them as `page=1` or ignoring the limit entirely. I considered the "just default it" approach first, since it seemed friendlier — but decided against it, because silently substituting a default hides a real bug from the client. If a frontend has a typo passing `?page=NaN`, silently defaulting to page 1 means that bug could ship to production and nobody would ever notice, since the API "worked" the whole time. Returning a `400` instead makes the mistake visible immediately, during development, which is exactly when it's cheapest to fix. The test suite specifically covers this (`page=-1` returns `400`, not a crash and not a silent default), which is what gave me the confidence to trust this decision rather than just assume it was working.

## Where centralized error handling prevented an inconsistent response

While building the pagination validation, I initially wrote the malformed-parameter check as a plain `res.status(400).json({...})` directly inside the `GET /notes` route, before remembering that the whole point of Task 2's centralized handler was that routes never format their own error responses. Once I converted it to `next(new ValidationError('Invalid pagination parameters', ...))` instead, I could immediately verify — via the test suite — that a pagination-validation failure and a `POST` body-validation failure return the **exact same envelope shape** (`{error: {message, code, details}}`), just with different messages. Had I left the pagination check as a one-off inline `res.status().json()`, it would have been trivially easy for that one endpoint's error shape to drift from every other endpoint's over time (a missing `code` field, a differently-named `details` key), and nothing in the codebase would have caught it. Routing it through the same `next(err)` path as every other error guarantees that drift is structurally impossible, not just something I have to remember to keep consistent by discipline.
